# Q4_K16_VQ: интеграция кодбук-кванта K=1024 (§10) — журнал работ

Дата: 2026-08-17. Источник ТЗ: `subProject_q4/docs/10_VQ_K1024_IMPLEMENTATION.md`.
Ветка: `research/q4-k16-quant`. Цель: GGUF-тип 55 `Q4_K16_VQ` — вариант
`Q4_K16_S` (суперблок 512, 32×16, блок 300 B, bpw 4.6875), у которого
вместо 5+5-битных scale/min на субблок хранится 10-битный индекс в общий
кодбук K=1024 пар (scale, min). Файл модели: 16.4 GB против 16.99 GB у
Q4_K16-M политики при SNR не ниже b77.

## 1. Реализовано (2026-08-17)

### C-ядро

- `ggml/include/ggml.h`: `GGML_TYPE_Q4_K16_VQ = 55`, `GGML_TYPE_COUNT = 56`.
- `ggml/src/ggml-common.h`: `block_q4_K16_VQ` — d(f16), dmin(f16),
  idx[40] (32×10-бит LSB-first), qs[256]; `static_assert(sizeof == 300)`.
- `ggml/src/ggml-vq-codebook.h`: кодбук 1024×2 float32, сгенерирован из
  `vq_codebook_k1024.npy` с полной точностью (round-trip bit-exact;
  .txt-версия округлена до 6 знаков и НЕ используется).
- `ggml/src/ggml-quants.c`:
  - `unpack_bits_u32`/`pack_bits_u32` — 10-битный битстрим (8-битные
    функции не годятся: индекс 0..1023 не влезает в uint8).
  - `quantize_row_q4_K16_VQ_impl(x, y, n, quant_weights)`:
    make_qkx2_quants как в impl_full → якоря d=f16(max_scale),
    dmin=f16(max_min) → распаковка якорей обратно в f32 → полный перебор
    кодбука на СУББЛОК (32 независимых индекса — как прототип
    `decode_vq_anchor`; «один индекс на суперблок» в §3 шаг 4 — опечатка
    ТЗ, формат §2 и код прототипа используют 32 индекса) → выбор по
    взвешенной ошибке (веса = сырые imatrix-значения БЕЗ sqrt-фактора,
    как wsub в прототипе; ошибки в double, последовательные суммы,
    уровни через nearbyintf((float)(...)) — f32 round-half-even как
    numpy-_rint) → финальный пересчёт уровней по упакованной мете
    (guard: d_f==0 → denom=1, иначе dd=max(d_f*cs, 1e-30);
    dmn=max(dmin_f*cm, 1e-30)) → упаковка qs (low nibble = чётный) и
    idx (pack_bits_u32, 10 бит).
  - `dequantize_row_q4_K16_VQ`: x = d_f*cs(idx)*L − dmin_f*cm(idx),
    f32-арифметика, одна LUT-выборка на субблок.
  - `quantize_q4_K16_VQ` — column-wise imatrix-обёртка (для
    `ggml_quantize_chunk`).
  - `ggml_validate_row_data`: VQ-кейс (d/dmin fp16 check; idx —
    произвольный битстрим).
- `ggml/src/ggml.c`: type_traits[55] — type_name "q4_K16_VQ",
  blck 512, size 300, to_float/from_float_ref; `ggml_quantize_chunk`-кейс.
- `ggml/src/ggml-cpu/ggml-cpu.c`: traits_cpu[55] — CPU dot-путь с F32
  RHS; каждый VQ-суперблок деквантуется точным `to_float`-путём перед
  скалярным произведением. Это корректный reference fallback до появления
  нативного q8-ядра. `ggml/src/ggml-cpu/quants.h`: декларация.
- VQ **не** добавлен в `ggml_is_q4_k16`/`ggml_q4_k16_packed_type`:
  loader загружает VQ как есть, без packed-репака (§6 «если нужен
  packed-layout» — не нужен, отдельного packed-типа 56 не вводилось).

## 3.3 Vulkan-бэкенд (2026-08-18, СДЕЛАНО)

**Ключевое решение: без репака при загрузке.** В отличие от Q4_K16
(типы 49–51 → 52–54 через `ggml_repack_q4_K16`), VQ читается шейдером
как есть. Блок 300 B уже выровнен на 4: `dm` в 0–3, `idx` = uint'ы 1..10,
`qs` = байты 44..299. Расширение 10-бит → u16 добавило бы 24 B на блок
(+1.14 GB VRAM на модель) ради устранения одного сдвига — не стоит того.

**Кодбук в шейдере.** `q4_k16_vq_codebook.glsl` — `const vec2[1024]`,
сгенерирован из `ggml/src/ggml-vq-codebook.h`; десятичные литералы
round-trip'ятся в те же float32, что и на CPU, поэтому dequant
бит-идентичен CPU-эталону. Вариант «SSBO/shared memory» отвергнут для
фазы 1: AMD отдаёт `maxComputeSharedMemorySize = 32768`, и 8 KiB LUT
давил бы на тайлы mul_mm; плюс новый binding пришлось бы протаскивать
через все пайплайны. Регенерация: regex
`\{\s*(-?[\d.eE+-]+)f,\s*(-?[\d.eE+-]+)f\s*\}` по C-хедеру, 2 пары в строку.

**Распаковка 10 бит — branchless и без выхода за границы:**

```glsl
#define Q4_K16_VQ_WORD(sb)  (((sb) * 10u) >> 5)
#define Q4_K16_VQ_WORD1(sb) (min(Q4_K16_VQ_WORD(sb) + 1u, 9u))
#define Q4_K16_VQ_SHIFT(sb) (((sb) * 10u) & 31u)
uint q4_k16_vq_unpack(const uint w0, const uint w1, const uint sh) {
    return ((w0 >> sh) | ((w1 << (31u - sh)) << 1u)) & 0x3FFu;
}
```

Второй сдвиг разбит на два, чтобы при `sh == 0` не получить сдвиг на 32
(UB в GLSL) и нулевой вклад; `min(...,9)` держит чтение в границах для
сдвигов, которым сосед не нужен.

**Изменённые файлы:** `types.glsl` (struct + макросы), `dequant_funcs.glsl`
(`dequantize4`, `get_dm` → `vec2(1,0)`), `mul_mm_funcs.glsl` (ветка
загрузки в `buf_a`), новый `dequant_q4_k16_vq.comp` (32 треда = 32
субблока на воркгруппу), `vulkan-shaders-gen.cpp`, `vk_shaders.inc`,
`vk_transfer.inc`, `vk_dispatch.inc`, `vk_backend_registry.inc`.

В `vulkan-shaders-gen.cpp` появился `is_q4_k16_packed()`: старый тест
`string_starts_with(tname, "q4_k16")` ловил бы и VQ, навязывая ему
`SC_BITS/MIN_BITS`-путь упакованных типов.

**MMQ (q8_1) для VQ не делается сознательно**: масштабы кодбука —
float'ы, а не целочисленные масштабы, на которые рассчитаны q8_1-ядра.
Бэкенд корректно откатывается на f32 mat-mat (`mmp == nullptr →
quantize_y = false`), и `ggml_vk_should_use_mmvq` возвращает false для
всего семейства Q4_K16_*.

**Сборка и проверка:**

- 62 SPIR-V шейдера `*q4_k16_vq*` сгенерированы; `ggml-vulkan` собран `rc=0`.
  Грабли: `vulkan-shaders-gen.exe` падал с `rc=127` без сообщения — MSYS-PATH
  подсовывал `/mingw64/bin` вместо `libstdc++-6.dll` от Strawberry g++ 13.2.
  Лечится `PATH="/c/Strawberry/c/bin:$PATH"` на каждый вызов.
- `test-backend-ops test -o MUL_MAT -b Vulkan0` → **978/978 passed**,
  включая все 10 кейсов `type_a=q4_K16_VQ`.
- Smoke: `llama-cli -m models/Qwen3.6-27B-Q4_K16-VQ.gguf -ngl 99 -c 2048
  -n 96 --temp 0` — связный корректный текст,
  `Prompt 17.2 t/s | Generation 27.2 t/s`.

**Побочно исправлен баг харнесса (не мой, предсуществующий).**
`test-backend-ops` падал на `GGML_ASSERT(view_src == NULL || ... <=
ggml_nbytes(view_src))` ещё до добавления VQ (проверено через
`git stash` + пересборку): формы хардкодят ne0/k = 256, что не кратно
512-блоку семейства Q4_K16, уже добавленного в `all_types`. Починено в
5 местах через `std::max(256, ggml_blck_size(type))`.

**Замечено, не чинилось (вне объёма).** В `mul_mmq_funcs.glsl` ветка
`DATA_A_Q4_K16` считает `d1 = dm.x * sc / (2^SC_BITS - 1)` и
`m1 = dm.y * m / (2^MIN_BITS - 1)`, тогда как CPU-эталон
`dequantize_row_q4_K16_P_impl` использует `dd = d_f * sc; dm = dmin_f * m`
**без** деления. Похоже на латентный баг существующего Q4_K16 MMQ-ядра
(вероятно, никогда не выбиралось). Аналогично,
`ggml_vk_get_dequantize_mul_mat_vec_id` перечисляет упакованные K16-типы,
хотя пайплайнов `mul_mat_vec_id_q4_k16*` не регистрируется — риск
null-пайплайна, если MoE-модель когда-нибудь их использует.

## 3.4 PPL-гейт (2026-08-18, ПРОЙДЕН)

Все прогоны: `llama-perplexity -f wikitext-2-raw/wiki.test.raw -c 512
-b 512 -ngl 99`, сборка `build-vulkan` (b9375).

| модель | размер | PPL 16ч | PPL 256ч |
|--------|--------|---------|----------|
| Q4_K16-outq6 | 15.82 GB | 7.3995 | 6.8345 ± 0.0676 |
| Q4_K16       | 15.32 GB | 7.4319 | 6.8483 ± 0.0677 |
| **Q4_K16-VQ**| **15.28 GB** | **7.4096** | **6.8516 ± 0.0679** |
| Q4_K_M       | 15.93 GB | 7.3941 | 6.8588 ± 0.0680 |

**Осторожно с разницей файлов — она наполовину не про формат.** Сравнение
«в лоб» (15.28 против 15.93 GB, −4.1%) завышено: у Q4_K_M есть MTP-голова
`blk.64.*` (15 тензоров, 0.270 GiB), которой в VQ просто нет. На одинаковом
наборе из 851 тензора: **VQ 15.272 против 15.652 GiB, то есть −2.4%.**

Механизм экономии обратный ожидаемому. Сам формат VQ *дороже* Q4_K на весе
(4.688 против 4.500 bpw); выигрывает он однородностью, а не плотностью:

| | состав |
|---|---|
| VQ | 400 тензоров × 4.688 bpw + 2 × Q6_K (embed/output) |
| Q4_K_M | 294 × Q4_K 4.500 + 48 × Q5_K 5.500 + 67 × Q6_K 6.5625 |

Q4_K_M вынужден поднимать 115 тензоров до Q5_K/Q6_K — 32-элементных
субблоков не хватает точности на attn_v и ffn_down. VQ с 16-элементными
субблоками точен везде и обходится одним типом. Средневзвешенно 4.877
против 4.998 bpw.

**И это ещё не паритет по возможностям.** Те 0.270 GiB у Q4_K_M —
не балласт, а MTP-голова, дающая self-speculative decoding. Пока голова не
сквантована в VQ-формат, сравнение остаётся в пользу Q4_K_M: он тяжелее,
но умеет больше. Корректный замер — 15.53 против 15.92 GiB при равной
функциональности.

**По PPL VQ и Q4_K_M неразличимы** (6.8516 против 6.8588 при ±0.068). Против
plain Q4_K16 разница +0.0033 (0.05%) — глубоко в шуме при ±0.068.
Цена VQ в SNR (§3.1, ~0.4–0.7 dB) на перплексии не проявляется.

**Про порог 6.60.** Он был взят из `PORT_LOG` (Q6_K 6.6012 / Q4_K16 6.6124 /
bf16 6.6202 / Q4_K_M 6.6253), но те числа несравнимы с текущей сборкой:
на 16 чанках Q4_K16 даёт 7.4319 против исторических 7.0196. Сначала это
выглядело как регресс VQ, потом — как регресс K16. Решил контрольный
прогон **Q4_K_M** (независимый от всей K16-ветки): 7.3941 против
исторических 7.0015, то есть +0.39 у *всех* моделей. Сдвинулась линия
измерения целиком, ветка K16 ни при чём. Вывод: сравнивать только
попарно на одной сборке; гейт переформулирован как «VQ ≤ Q4_K_M».

**Префилл стоит −7.3% против Q4_K16** (−10.5% против Q4_K_M). Это цена
распаковки 10 бит + косвенности через кодбук в `mul_mm_funcs.glsl`, где
`const vec2[1024]` компилятор, судя по всему, не держит эффективно.
Первый кандидат на оптимизацию — перенести LUT в shared memory
(`NEEDS_INIT_IQ_SHMEM`/`init_iq_shmem`, 8 KiB из 32 KiB) именно для
mat-mat: в фазе 1 этот вариант отвергли из-за давления на тайлы, но
теперь есть цифра, с которой можно сравнивать.

Грабли при замере: `llama-bench.exe` был устаревшим бинарником и падал с
`invalid ggml type 55 ... should be in [0, 49)` — пересборка только
таргета `ggml-vulkan` его не обновляет. Полный `cmake --build build-vulkan`
при этом ломается на предсуществующей ошибке в `tests/test-llama-archs.cpp`
(`LLM_ARCH_QWEN35_MTP` не объявлен), к VQ отношения не имеет.

## 3.6 Кодбук в shared memory (2026-08-18, СДЕЛАНО)

Решение фазы 1 (§3.3) пересмотрено по цифрам из §3.5: LUT стейджится в LDS,
но **только для mat-mat**. Там воркгруппа делает много обращений и 8 KiB из
32 KiB окупаются; mmv и dequant читают кодбук считанные разы и остаются на
`const`-массиве. Развилку держит `Q4_K16_VQ_SHMEM_LUT`, который
`vulkan-shaders-gen.cpp` выставляет только для matmul-стадий, и макрос
`Q4_K16_VQ_CB(i)` в трёх точках чтения. `init_iq_shmem` повторяет
существующий паттерн `kvalues_iq4nl`. Бюджет учтён в
`ggml_vk_matmul_shmem_support` (`lut_size = 8*1024`), иначе тайлы могли бы
не пройти проверку на устройствах с меньшим LDS.

| LUT | VQ pp512 | Q4_K16 pp512 | VQ/K16 |
|-----|----------|--------------|--------|
| `const` | 949.4 ± 1.7 | 1023.9 ± 9.7 | 0.927 |
| LDS | 1004.6 ± 3.2 | 1028.2 ± 1.4 | 0.977 |

**Префилл +5.8%** (949.4 → 1004.6) при неизменной базовой линии; отставание
от Q4_K16 сократилось с −7.3% до −2.3%. Декод не изменился (29.18 против
29.29 — в шуме, tg упирается в память). `test-backend-ops -o MUL_MAT`
978/978, PPL 16ч = 7.4096 — ровно как с `const`-массивом, то есть
стейджинг численно точен.

**Методическая грабля (важно для будущих замеров).** Первый прогон после
правки показал деградацию всего, включая нетронутый Q4_K16: 1023.9 → 822.5
при разбросе ±64 вместо ±10. Откат правки через `git stash` дал
базовому Q4_K16 те же ~822 — значит виноват не код, а троттлинг после часа
PPL-прогонов. Абсолютные t/s между сессиями замера несравнимы; сравнивать
надо **отношение VQ/Q4_K16 внутри одного прогона** — оно оказалось
устойчивым (0.927 на холодном и 0.929 на горячем GPU для `const`-варианта).
Признак негодного замера — разброс `llama-bench` больше ~±1%.

## 3.7 Догоняем Q4_K_M (2026-08-19, СДЕЛАНО)

Отправная точка — ночной SWE-прогон (`build_logs/swe-overnight/night/summary.md`,
1160 задач, 9:03:07, 0 ошибок). Отношения VQ/Q4_K_M: prefill 0.665 (ub128)
и 0.912 (ub512), decode 0.941/0.936. На `llama-bench` то же самое читалось
как pp 0.838/0.935 и tg 0.925.

**Все замеры ниже — отношения внутри одного вызова `llama-bench`**, где
`Q4_K_M` идёт контролем в том же прогоне (см. методическую граблю в §3.6).

### Декод: выделенный mat-vec шейдер

Причина отставания оказалась структурной: `vulkan-shaders-gen.cpp` даёт
выделенный `mul_mat_vec_<tname>.comp` только типам на `_k`/`iq[123]_`, а VQ
падал на generic-путь. Контрольный опыт развёл два вклада: Q4_K_S
(выделенный, 15.00 GiB) 31.75 t/s против Q4_K16 (generic, вообще без
кодбука, 15.31 GiB) 28.64 — **generic-путь стоит ~8%**; VQ 27.81 — сам
кодбук добавляет ещё ~3%.

Написан `mul_mat_vec_q4_k16_vq.comp` по образцу `mul_mat_vec_q4_k.comp`.
Ключ — тождество `dot(y,b) = d*cs*Σ(l*b) − dmin*cm*Σ(b)` на субблок: одно
обращение к кодбуку на субблок, `d`/`dmin` применяются один раз на
суперблок, а не на каждое значение. `b` предварительно свизлится под
чётные/нечётные ниббли, `Σ(b)` считается один раз на все строки.
Decode 0.925 → **0.969**.

Замеры остаточной стоимости (все с контролем): базовая 0.969, «кодбук в
полцены» 0.9725, «рассеянный индекс» 1.0055, «без idx-загрузки» 1.013,
«без обращения к кодбуку» 0.975. Вывод: разброс адресов гатера стоит <1%,
а **зависимая цепочка `idx`-загрузка → гатер кодбука — ~3.6%**. Сужение
гатера до 4 байт (f16-кодбук) даёт всего 0.4% и не стоит потери точного
совпадения GPU==CPU на f32.

### Префилл: векторная распаковка нибблов

Оставшийся провал именно на ub128 (0.842 при 0.941 на ub512) не объяснялся
ни кодбуком (с «бесплатным» кодбуком ub128 давал 0.878 против 0.995 на
ub512), ни MMQ (`GGML_VK_DISABLE_INTEGER_DOT_PRODUCT=1` не менял ничего),
ни бюджетом LDS.

Нашлось при построчном сравнении с загрузчиком Q4_K: тот берёт четыре
ниббла одной инструкцией `unpack8`, а загрузчик VQ делал восемь скалярных
сдвигов с маской и восемь скалярных `fma`. Замена на два `unpack8` и два
векторных `fma` на 8 значений:

| ubatch | было | стало |
|--------|------|-------|
| pp512 @ ub128 | 0.842 | **0.972** |
| pp512 @ ub512 | 0.941 | **0.947** |

То есть «структурный» провал ub128 — это была чистая ALU на распаковке;
на ub512 путь и так упирался в память, поэтому там прирост в пределах 1%.

### Отвергнутые гипотезы

| Кодбук в LDS для mat-vec | быстрее | 0.876 (generic) / 0.903 (выделенный) против 0.969 — только mat-mat выигрывает от LDS |
| Спаривание соседних субблоков в mmv (вдвое меньше загрузок `idx[]`) | быстрее | 0.935 против 0.969 — все десять слов `idx` и так в одной кэш-линии, а селекты стоят ALU |

### Не подтверждено end-to-end

Контрольный прогон SWE-harness завален по моей вине: не передал
`--ctx-size`, взялся дефолт драйвера 131072 вместо ночных 32768. KV-кэш
вырос вчетверо и у VQ не влез в VRAM — 432 MiB уехали в
`Vulkan_Host_Direct`, то есть за PCIe. Оттуда «prefill 649 t/s против
ночных 952» — это замер шины, а не шейдеров. Признак, что тракт исправен:
сток в обоих прогонах дал одинаковые 1433/1438.

Так что цифры выше подтверждены только на `llama-bench`. Для end-to-end
нужен повтор с явным `--ctx-size 32768`.

Побочно всплыло: при ctx 128k VQ балансирует на грани VRAM и слои легли
по картам несимметрично (7039/7613 MiB против ровного сплита у стока).
Экономия 0.38 GiB на весах здесь съедается неудачным распределением.

## 4. Производительность и предфильтр (§9)

Полный перебор 1024 центров на субблок — слишком медленно для сборки
файла (оценка ~5 ч при 1 job). Реализован L2-предфильтр (§9): топ-K
центров по дистанции в нормированном пространстве
(s_j/d_f, m_j/dmin_f), затем взвешенный перебор по кандидатам;
кандидаты сортируются — ничьи по err резолвятся в наименьший k, как в C.

Свип дельты SNR (blk.10, 64 строки, imatrix):

| TOP_K | ffn_gate | ffn_down |
|-------|----------|----------|
| 128   | 25.2087 (−0.0525) | — |
| 256   | 25.2382 (−0.0230) | — |
| 512   | 25.2542 (−0.0070) | 25.5841 (−0.0084) |
| 1024  | 25.2612 (полный)   | 25.5925 (полный) |

**Принято: top_k=512** — дельта ≤ 0.01 dB, ~1.6× быстрее полного перебора.
