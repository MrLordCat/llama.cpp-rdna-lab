# P2 MMVQ Decode And Linker Blocker

## Objective

Remove MMVQ experimentation blocker (amdgcn-link failures) and enable targeted decode-path optimization for Qwen-heavy quantized types.

## Code study map

- ggml/src/ggml-cuda/mmvq.cu
  - get_mmvq_mmid_max_batch() and per-arch batch tables
  - calc_nwarps() architecture/type decision tables
  - mul_mat_vec_q<type, ncols_dst, ...>() kernel template
  - mul_mat_vec_q_switch_ncols_dst() and mul_mat_vec_q_switch_type()
  - ggml_cuda_mul_mat_vec_q() and ggml_cuda_op_mul_mat_vec_q()
- ggml/src/ggml-cuda/mmq.cuh
  - MMQ routing and tile policy context (prefill-oriented traces)

## What is currently known

- Active decode matvec path is MMVQ, while MMQ traces are mostly informative for prefill on this lane.
- Direct MMVQ source edits have repeatedly triggered amdgcn-link failures.
- Restricting type switch to Qwen-relevant Q3_K/Q4_K/Q6_K did not remove the linker blocker.

## Root-cause hypothesis

Template and symbol pressure in mmvq.cu remains too high for current ROCm Windows link stage even after partial switch reduction, so compile-time decomposition is required before kernel tuning can proceed safely.

## Solution strategy (implementation later)

1. Translation-unit decomposition
- Split MMVQ dispatcher and kernel instantiations into smaller, targeted compilation units.
- Isolate Qwen hot quantized types from long-tail types.

2. Dispatch boundary cleanup
- Keep one thin entry dispatcher that routes to per-type implementation files.
- Avoid giant switch-and-template fanout in one translation unit.

3. Controlled tuning surface
- Add compile-time or runtime gated tuning tables for nwarps and related parameters per hot type.
- Keep defaults unchanged unless an experiment flag is enabled.

## Planned code changes (not applied yet)

- ggml/src/ggml-cuda/mmvq.cu
  - Reduce to front dispatcher and shared helpers only.
- new files under ggml/src/ggml-cuda/
  - mmvq-kernels-qk.cu (Q3_K/Q4_K/Q5_K/Q6_K focus)
  - mmvq-kernels-misc.cu (other quantized types)
  - mmvq-dispatch.cuh (shared dispatch interface)
- ggml/src/ggml-hip/CMakeLists.txt
  - Add new source files and keep reduced-experiment compatibility.

## Validation plan (after implementation)

Build gates:

1. Reduced corridor build (compile sanity)
2. Normal ROCm build (integration sanity)
3. No unresolved symbols and no link-stage signal failure

Runtime gates:

1. Decode-focused short lane comparison on active model
2. Full v2-review aggregate TPS comparison
3. Prompt and decode metrics reported separately

Acceptance criteria:

- Build reliability restored for MMVQ edits.
- Decode eval TPS improves without prompt regressions.
- Wall TPS improvement is reproducible on active lane.

## Risks

- TU split can increase maintenance complexity if shared templates are duplicated.
- Incorrect dispatch wiring can silently change kernel selection.
- Build-time improvements may not translate into runtime speedup.

## Rollback criteria

- Any non-deterministic link behavior after split.
- Any functional mismatch in outputs vs baseline.
- Any wall performance regression larger than noise.

## Open questions

- Which subset of template instantiations dominates link pressure on this machine?
- Should type partitioning be static or generated by CMake options for experiments?
